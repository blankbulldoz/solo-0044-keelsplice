# 认证子库接收兼容说明

面向接收 Keelsplice 认证子库（`.sqlite` 文件加证书）的一线维护者。说明同一份签过证书的文件对两个下游分别意味着什么、什么时候可以放行、什么时候必须请求另一份交付。配套的可复跑验收见 `examples/acceptance_compat.py`，源输入见 `examples/handoff_compat.sql`。

## 1. 交付边界（先记住这三条）

工作台的数据契约（见 `PROJECT_SPEC.md`）决定了认证子库的内容：

1. **普通表全部交付，包括没有入选任何行的表。** 表定义、声明的约束（主键、外键、`NOT NULL`、`WITHOUT ROWID`、生成列等）原样重建。
2. **显式索引全部交付**，含部分索引（带 `WHERE` 的索引），定义 SQL 与源库一致。
3. **视图和触发器不属子库交付范围。** 目录阶段就跳过视图、从不登记触发器，因此证书也不覆盖它们。子库里查不到源库的视图和触发器，这是预期行为，不是损坏。

证书（`GET /captures/{id}` 返回的 `certificate`）只担保四件事：文件字节的 SHA-256、字节数、模式摘要（表 + 显式索引 + 外键）、逐表入选行数，外加认证连接上的完整性检查与外键检查。**证书不担保视图、触发器，也不担保未入选的行。**

## 2. 三类情况怎么分清

验收脚本用一个可复跑源库把三种情况摆在一起。源库里 `staging_area` 有 2 行，但配方闭包选不中它；源库还有视图 `recent_events` 和触发器 `event_log_insert_note`。

| 情况 | 子库里的观察 | 含义 | 验收脚本对应断言 |
| --- | --- | --- | --- |
| 没有入选行 | `SELECT count(*) FROM staging_area` 为 0，且与 `certificate.counts` 一致 | 该表在本次选样范围外，不是丢表 | `情况一` |
| 结构仍在 | 0 行表的 `CREATE TABLE`、`NOT NULL` 约束、部分索引定义都在，违反约束的插入仍被拒 | 可据此初始化自己的数据 | `情况二` + 初始化型下游演练 |
| 功能对象根本不交付 | `sqlite_schema` 中 `type IN ('view','trigger')` 为空，查询视图报 `no such view` | 源库行为无法在子库延续，与证书有效性无关 | `情况三` + 行为延续型下游演练 |

零行和缺表是两回事：**零行是数据范围问题，缺表是结构问题。** 认证子库允许零行，不允许缺表——缺表会改变模式摘要，认证阶段直接失败，文件根本到不了下载环节。

## 3. 两个下游的放行决策

### 下游 A：初始化型应用（依赖空表仍有 DDL）

它只需要表和约束存在，以便自己建结构、灌数据。

**可放行**，当且仅当：

1. 文件 SHA-256 与证书 `sha256` 一致；
2. `PRAGMA integrity_check = ok` 且 `PRAGMA foreign_key_check` 无违例；
3. 它依赖的每张表都能在 `sqlite_schema` 找到，列与约束符合约定（零行表也算满足）；
4. 需要的显式索引存在。

### 下游 B：行为延续型应用（把源库视图和索引行为视为可继续使用）

拆成两半判断：

- **索引行为：可放行。** 显式索引随子库交付，定义一致，`EXPLAIN QUERY PLAN` 能选到交付的索引。
- **视图/触发器行为：不可放行。** 认证子库不交付这些对象，证书也不覆盖。应用若打开视图会直接收到 `no such view`，依赖触发器自动写入的逻辑不会发生。

**此时应请求另一份交付**，要求上游补充：

1. 视图和触发器的 DDL 文本（建议与源库 `sqlite_schema.sql` 逐字一致或给出变更说明）；
2. 在认证子库上安装这些对象的操作记录；
3. 安装后重新复核的证据：视图可查询且结果口径与源库一致、触发器按预期触发、安装动作没有改动认证表的数据（安装后重算表行哈希或重新封存对比）。

注意：在子库上手工安装视图/触发器会改变文件字节，原证书的 SHA-256 不再匹配新字节。补充交付应自带新的复核记录，不能继续只引用原证书。

### 决策速查

| 观察 | 下游 A | 下游 B |
| --- | --- | --- |
| 摘要不符 / integrity_check 失败 | 拒收，请求重新交付 | 拒收，请求重新交付 |
| 依赖的表缺失 | 拒收（正常认证流程不会出现，出现即说明文件被替换或损坏） | 同左 |
| 表为零行但 DDL、约束、索引齐全 | 放行 | 放行 |
| 显式索引缺失或定义变化 | 按需评估；模式摘要应已变化，先怀疑文件与证书不配套 | 同左 |
| 源库视图/触发器在子库不存在 | 不涉及，照常放行 | 就视图/触发器部分请求另一份交付；索引部分不受影响 |

## 4. 复跑验收

```sh
python3 -m examples.acceptance_compat
```

脚本使用临时目录：从 `examples/handoff_compat.sql` 建源库，经真实 HTTP 工作台完成登记配方、试算、封存、构建、认证、下载，再用独立只读 SQLite 连接复核三类情况，并分别模拟两个下游。退出码 0 表示全部断言通过。它还会制造一个单比特翻转的副本，演示摘要不符的文件必须被挡在门外。

## 5. 手工复核语句（应急时直接在子库上执行）

```sql
PRAGMA integrity_check;
PRAGMA foreign_key_check;
SELECT type, name FROM sqlite_schema WHERE name NOT LIKE 'sqlite_%' ORDER BY type, name;
SELECT count(*) FROM staging_area;                              -- 预期 0：没有入选行
SELECT sql FROM sqlite_schema WHERE name = 'staging_tenant_lookup';  -- 预期部分索引定义仍在
SELECT * FROM recent_events;                                    -- 预期 no such view：功能对象未交付
```

## 6. 常见误判

- **“表查得到但 count 是 0，交付不合格”** —— 错。零行表保留 DDL 正是契约的一部分，核对 `certificate.counts` 即可。
- **“证书有效所以视图也该能用”** —— 错。证书范围不含视图和触发器，能打开数据库不等于功能等价。
- **“自己在子库里补个视图就继续用原证书交接”** —— 不行。补对象改动字节，原 SHA-256 失效，必须带新的复核记录另行交付。
- **“外键检查通过就说明数据完整”** —— 不完整地说。外键检查只说明入选行之间参照闭合；未入选的行本来就不在交付范围内，完整性以证书计数和模式摘要为准。
