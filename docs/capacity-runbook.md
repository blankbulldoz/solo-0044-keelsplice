# 关系采样容量处置说明（值班组）

本说明面向在 Keelsplice 关系样本工作台值班、需要快速判断一次试算/封存为什么被容量挡住的工程师。配套两份可复跑的 SQLite 小样和一个对照脚本，帮助用**实际观测**而不是猜测来选择处置手段。

## 1. 三道容量上限从哪里来

闭包采集在一次源读事务内运行，代码里有三道相互独立的硬上限。它们的检查点、错误码和计量单位都不同：

| 上限 | 错误码（JSON `error`） | 检查位置 | 计量对象 | 阈值 |
| --- | --- | --- | --- | --- |
| 行上限 | `row_budget` | `capture.collect` 的 `add()`，每个**新去重行**入库前 | 闭包内去重后的行总数 | 配方 `row_limit`，1–5000，默认 1000 |
| 见证上限 | `edge_budget` | `capture.collect` 的 `witness()`，每条**关系见证弧**入库前 | 直接关系证据（arc）条数，不去重 | 固定 50000 |
| 读工作量上限 | `scan_budget` | `storage.source` 的 SQLite 进度处理器 | 单条源连接内累计的 VDBE 指令，每 1000 条计一次 tick | 超过 5000 个 tick（约 5,000,000 条指令）中断当前 SQL |

三个关键事实，决定了后面的判断逻辑：

1. **行按身份去重，见证不去重。** 同一行被多个父行重复命中时，只占一个行名额，却会为每次命中各产生一条见证弧。因此见证数可以远大于行数。
2. **见证在上限检查时先于行计入。** `witness()` 内部先检查 50000 弧上限，再调用 `add()`；一行既触发新行又触发新弧时，弧预算先被检验。
3. **读工作量在整个源连接上累计，且与返回行数无关。** 一次 `SCAN` 即使只返回 0 行，扫描过的指令照样计费；目录读取（PRAGMA）也在同一连接内计费。

> 另有一个 `payload_budget`（8 MiB，序列化后的行+见证字节），本说明的小样刻意不触碰它；真实环境若先撞到它，错误码会明确给出，处置思路与 `edge_budget` 同源（减少被采集的列/边）。

## 2. 两份小样各自先撞哪道墙

两份库由 `examples/capacity_seed.py` 生成，业务规模同量级（数千到一万多行），但形状相反：

| 文件 | 表与规模 | 形状特征 | 同一基线配方先撞 |
| --- | --- | --- | --- |
| `capacity-labs/capacity_dense.sqlite` | `hub` 24 行；`evt` 2500 行，每行 12 个指向 `hub` 的外键 | 小表、多外键、高度复用：一个根的闭包就能覆盖全部 24 个 hub | **见证上限 `edge_budget`** |
| `capacity-labs/capacity_scan.sqlite` | `customer` 32 行；`event` 18000 行，含 58 行可达自引用链，`parent_eid`/`cid` 无索引 | 宽表、窄闭包：闭包只有约 59 行，但每跳反向查找都全表扫描 | **读工作量上限 `scan_budget`** |

行上限不是某个库的固有属性，而是配方 `row_limit` 的结果——小样 A2 演示如何把同一库压到先撞 `row_budget`。

### 2.1 为什么 dense 库先撞见证上限

`evt` 的 2500 行每行携带 12 条外键。采集时见证弧有两个来源，必须区分：

- **父方向见证（`direction=parent`）**：每个被选入行都要解析其全部外键的必需父行，这**不受 `follow_children` 控制**。2500 个 `evt` 行各 12 条外键，产生约 2500 × 12 = 30000 条父方向弧。
- **子方向见证（`direction=child`）**：只来自配方显式选择的反向边。每条被选反向边在 BFS 展开时，对每个命中的 `evt` 再产生一条弧。

实测（脚本可复算）：选 3 条反向边时共 37500 弧（30000 父 + 7500 子），选 6 条时 45000 弧（30000 父 + 15000 子），12 条全选时子方向弧继续累积并在 5000 行之前越过 50000 弧上限。而去重行始终只有约 2524 个身份，离 5000 行上限还很远。

这是「**弧密度高**」的典型：边/行比远大于 1（6 条边时约 17.8 条弧/行）。注意父方向弧由 schema 的外键数量决定，收紧 `follow_children` 只能削掉子方向那一部分。

### 2.2 为什么 scan 库先撞读工作量上限

反向子查询在 `capture.children` 中形如：

```sql
SELECT c.* FROM "event" p JOIN "event" c
  ON p."eid" = +c."parent_eid" WHERE p."eid" = ?
```

列前的一元 `+` 会取消该列的亲和性，**SQLite 因此放弃普通索引，执行计划恒为 `SCAN c`**（对照脚本会把真实计划打印在 `scan_lab_reverse_lookup_plan` 字段）。自引用链有 58 跳，每跳都把 18000 行的 `event` 表完整扫一遍，累计 tick 在闭包长到 59 行之前就越过 5000。作为参照，源侧归档后同样的链能成功采集：59 行仅产生 172 条见证（115 条父方向 + 57 条子方向），行和见证预算都远未用满——挡住基线的纯粹是读工作量。

这是「**单跳查询贵**」的典型：与闭包大小无关，与被扫表的体量和计划有关。

## 3. 三种处置分别什么时候有效

值班动作只有三类：**收紧反向关系**（改 `follow_children`）、**减小输入**（改根集合）、**安排源侧检查**（让 DBA/源系统改表或做留存）。下表给出判定依据，全部可用第 4 节的对照复跑验证。

| 处置 | 对 `row_budget` | 对 `edge_budget` | 对 `scan_budget` |
| --- | --- | --- | --- |
| 收紧反向关系（少选/不选外键边） | 有效，但仅当超量行来自**反向（子）遍历**；父行（必需父键）不受 `follow_children` 控制，收紧无效 | **首选**：直接削掉子方向见证（A1 把 12 条边降到 6 条，子弧减半后整体降到 45000）。注意父方向见证由外键列数决定，收紧边无法削这部分 | 仅当去掉的正是触发昂贵 `SCAN` 的那条边时有效（见 B1）；否则无效 |
| 减小输入（更少/更窄的根） | 当闭包随根线性增长时有效 | 当不同根覆盖**互不相交**的子图时有效；若根的闭包已完全重叠，加根/减根不改变结果（见 A3） | 当昂贵扫描由被根拉入的子树触发时有效（见 B2/B3）；若单次查找本身就超预算，减根无效 |
| 源侧检查（留存归档、分区缩表；普通加索引对带 `+` 的查询无效，见 3.1） | 不直接解决行数问题；但能确认是否有异常扇出/脏数据撑大闭包 | 不直接解决弧数；用于确认复用度和外键设计是否符合预期（外键列越多，父方向弧越密） | **不改工作台代码时唯一能根治的方向**（见 B4）：缩小被扫表，让每条 `SCAN` 的累计指令留在预算内 |

### 3.1 关于「加索引」的重要陷阱

scan 库里即使补上 `CREATE INDEX event_parent ON event(parent_eid)`，执行计划仍是 `SCAN c`，`scan_budget` 依旧——因为工作台的子查询用 `+` 固定取消了亲和性。实测中连 `INTEGER PRIMARY KEY`（rowid 别名）一旦写成 `+列名` 也会退化为 `SCAN`，所以**在工作台现有查询写法下，源侧加普通索引、甚至依赖 rowid 别名都不会被采用**。源侧检查不能停留在「有没有索引」，而要用 `EXPLAIN QUERY PLAN` 核对**工作台实际发出的那条带 `+` 的 SQL** 的计划。已验证可靠的源侧手段是：

- 数据留存/分区，把无关历史行移出注册源（B4 的归档副本即如此，同配方立刻通过）；
- 压低单表体量，使每条 `SCAN` 的累计指令留在预算内（这是不改工作台代码时最稳妥的手段）。

若希望从根上让反向查找走索引，需要工作台侧调整子查询的亲和性写法（去掉抑制索引的一元 `+` 或改写连接条件），这属于工作台变更而非源库调优，应走正常发布流程，不能在值班时临时改源库绕过。

## 4. 如何复跑这套有区分力的对照

```sh
# 1) 生成两份小样（已存在则先清理，输出字节逐次一致）
python3 -m examples.capacity_seed capacity-labs

# 2) 起真实 HTTP JSON 服务，跑全部对照并打印 JSON 报告
python3 -m examples.capacity_replay capacity-labs
```

`capacity_replay` 不依赖手工截图：它对每个场景登记真实配方版本、调用 `POST /preview`，并把观测到的首个错误码或成功摘要写进报告；结尾 `matched` 字段为 `false` 时进程以非零退出，便于发现工作台或 SQLite 行为漂移。

| 场景 | 配方改动（相对基线） | 期望观测 | 说明了什么 |
| --- | --- | --- | --- |
| A0 | 12 条反向边，`row_limit=5000` | `edge_budget` | dense 基线先撞见证墙 |
| A1 | 反向边减到 6 条 | 成功（45000 弧 / 2524 行） | **收紧反向关系**直接解除见证上限 |
| A2 | 仍是 12 条边，`row_limit=100` | `row_budget` | 同一库可被配方压成先撞行墙；此时错误码改变诊断 |
| A3 | 再加两个 hub 根 | 仍 `edge_budget` | 闭包已被单根覆盖，**减小输入无效**的判据 |
| B0 | 自引用反向边，`row_limit=5000` | `scan_budget` | scan 基线先撞读工作量墙 |
| B1 | 去掉该反向边 | 成功（仅 1 行 1 弧） | 收紧掉昂贵边即可避开扫描 |
| B2 | 改用 `customer` 根、保留自引用边 | 成功（0 个 event 子行） | **减小输入**让昂贵子树不被拉入 |
| B3 | `customer` 根只走 customer 外键 | 成功（59 行 / 173 弧） | 换一条便宜的边，绕开自链扫描 |
| B4 | 源侧归档后用**同一配方** | 成功（59 行 / 172 弧） | **源侧留存**根治读工作量，配方无需改 |

手工复核单条计划（在注册的源文件上）：

```sh
sqlite3 capacity-labs/capacity_scan.sqlite \
  "EXPLAIN QUERY PLAN SELECT c.* FROM event p JOIN event c
   ON p.eid = +c.parent_eid WHERE p.eid = 1;"
# 期望看到 SCAN c，证明反向查找在全表扫描
```

## 5. 只知道「哪道上限先到」时，能下多强的判断

错误码只告诉你**第一道**撞上的墙，不告诉你另外两道墙离得多近。结论强度应分级：

### 观测到 `row_budget`

- **能确定：** 当前配方下闭包的去重行数已达到 `row_limit`，且这是最先到达的上限。
- **不能确定：** 超量行来自反向遍历还是必需父行；放宽 `row_limit` 后会不会接着撞 `edge_budget` 或 `scan_budget`。
- **下一步最小实验：** 在 A2 与 A0 之间对照——保持边不变只放宽 `row_limit`，看新的首个错误码。若变成 `edge_budget`，说明真正瓶颈是弧密度；若变成 `scan_budget`，说明还有计划问题。先不要直接申请扩到 5000。

### 观测到 `edge_budget`

- **能确定：** 关系图是见证密集型（弧/行比高），瓶颈在被选外键的数量与复用度，不在去重行数——因为弧检查先于行检查触发。
- **能较强判断：** 收紧反向关系大概率有效（A1 直接验证）。
- **不能确定：** 减根是否有用，除非已知各根闭包是否相交。A3 表明单根已覆盖全图时减根完全无效。**先查闭包相交性，再决定要不要动根。**

### 观测到 `scan_budget`

- **能确定：** 至少有一条源查询的执行计划昂贵（典型为 `SCAN`），且累计指令在闭包装满行/弧预算之前就超了。这与你选了多少行无关。
- **能较强判断：** 单纯调大 `row_limit` 或删根之外的配方微调通常无效；问题在源侧计划或表体量。
- **不能确定：** 是哪一条边、哪一跳触发的，以及缩表要缩到多少才够。**必须用工作台实际发出的带 `+` 的 SQL 跑 `EXPLAIN QUERY PLAN` 定位 `SCAN`，再决定留存/分区把表压到多小；不要先尝试加普通索引（见 3.1，对该写法无效）。**
- 收紧反向关系/减根在「能让那条昂贵 SQL 完全不执行」时可以临时解封（B1/B2），但属于绕开而非根治。

### 通用原则

- 一次只改一个变量（边集合、根集合、`row_limit`、源表），用 `capacity_replay` 的对照方式记录前后首个错误码，才能把相关性变成因果判断。
- 任意处置后若首个错误码**换成了另一道墙**，说明原瓶颈已解除、新瓶颈暴露——这是进展，不是失败，按新错误码回到本节对应分支。
- 处置在小样上验证可行后，再把同样的配方改动或源侧建议迁移到生产源；不要在生产上直接试 5000 行/256 根的极限配方。
