# 技术决策记录：工作台历史上下文的保存位置（浏览器 vs 服务端）

- 日期：2026-11-24
- 状态：提议（评审可通过文末复跑步骤验证全部论据）
- 复跑脚本：`examples/history_context_drill.py`（对真实 HTTP 服务注入故障，非文档推测）

## 1. 背景与问题

工作台需要保存两类"历史上下文"：

1. **多标签页草稿**：操作员在多个浏览器标签页打开「登记配方」页，表单内容（根 JSON、外键勾选、行上限）在提交前需要可恢复。
2. **旧捕获对照**：操作员对比两个封存捕获后，会话上下文（对比的是哪对捕获、当时的结论、当时的源状态）需要可复访。

待决问题：这些上下文保存在**浏览器**（localStorage 式草稿 + 不透明引用）还是**服务端**（状态库内的草稿/会话表）。本记录不泛泛比较，而是用两次受控注入回答一个更尖锐的问题：**两种保存位置各自在何处出现"看起来恢复成功但证据不成立"**。

## 2. 现状事实（代码依据）

- 编辑页把当前目录摘要放进隐藏字段随表单提交（`keelsplice/web/templates/recipe_editor.html:8`），服务端在登记时比对，不一致则 409 `browser_schema`（`keelsplice/service.py:25-26`）。
- 外键在表单里是位置性 token `{外键id}:{子表}`（`keelsplice/web/selection.py:17`）；登记只校验该 token 在当前模式中存在（`keelsplice/recipe.py:40`），不校验它指向哪条关系。
- SQLite 按外键子句**逆序**分配外键 id（本记录 §4 实测）：重建表并调整子句顺序后，同一 token `0:assay` 指向另一条外键。
- 已登记配方与源模式绑定摘要，试算/封存前重读源并比对，不一致则 409 `schema_conflict`（`keelsplice/service.py:47-48`）。
- 捕获封存后不可变，对比只接受同摘要的两个捕获（`keelsplice/capture.py:121-122`）；摘要只覆盖结构，不覆盖数据。
- 规格已声明「试算结果只对应本次读快照。封存发起独立读取。配方及试算都不代表未来封存的数据内容」（`PROJECT_SPEC.md:28`）。

## 3. 决策

**按证据职责分层放置，并对恢复路径订立校验契约**（选项 C，理由见 §8）：

1. **证据性上下文的权威副本在服务端状态库**：目录摘要、外键语义身份（`parent`/`child`/`child_cols`）、封存引用、证书、对比会话及其注释。
2. **草稿正文可以放浏览器**（多标签页体验所必需），但草稿必须同时携带**摘要 + 语义身份**；恢复时摘要与当前目录不一致必须显式阻断并要求重选，**禁止静默重绑新摘要**——把现有提交时的 409 提前到恢复时。
3. **派生结论永不作为恢复有效性的证据**：试算计数、对比摘要、"当前源状态"不得以"当前"名义落库；确需缓存时必须标注读快照边界且不参与恢复校验。
4. **存储层一律把外键 token 展开为语义身份**，位置 id 仅用于显示。

## 4. 实验设计与复跑

矩阵：两类案例 × 两次注入，使**两种保存位置各遇到一次假成功恢复**。

| | 结构漂移（重建 `assay`，外键子句重排） | 数据变化（`S-01` 改属另一父键） |
| --- | --- | --- |
| 多标签页草稿 | **浏览器保存假成功（C3）**；服务端保存响亮失败（C5） | （由案例二覆盖） |
| 旧捕获对照 | （由案例一覆盖） | **服务端保存假成功（C6）**；浏览器引用式重放成立（C7） |

复跑：

```sh
python3 -m compileall -q keelsplice examples
python3 -m examples.history_context_drill
```

脚本起两个独立的临时服务实例，注入一次结构漂移、一次数据变化，对 7 条主张（C1–C7）逐一断言。实际输出（2026-11-24 复跑）：

```
== 案例一：多标签页草稿 × 结构漂移（浏览器保存） ==
  D0=c44f76b50609… 0:assay 在 D0 下 = substrate→assay
  草稿时代闭包计数 {'assay': 2, 'cassette': 2, 'frame': 0, 'substrate': 1}
  D1=c60fa3f93c4c… 漂移后 0:assay=cassette→assay，1:assay=substrate→assay  [C1]
  过期标签页提交 409（browser_schema）；已登记配方试算 409（schema_conflict）  [C2][C4]
  恢复提交→登记→试算→封存全绿，但 0:assay 已指向 cassette，闭包计数变为 {'assay': 0, 'cassette': 0, 'frame': 0, 'substrate': 1}  [C3 假成功]
  对照：服务端草稿恢复时摘要不等（响亮），语义身份重定位 token 0→1  [C5]
== 案例二：旧捕获对照 × 数据变化（服务端保存） ==
  恢复校验 {'左捕获存在': True, '右捕获存在': True, '摘要一致': True} 全绿，但缓存计数 {'assay': 2, ...} ≠ 当前源计数 {'assay': 1, ...}，B×C 对比显示 S-01 已移出闭包  [C6 假成功]
  对照：引用式历史重放 A×B 逐字一致，当前源状态重新求值即刻可见；会话注释（B 为 7µm 修正候选／S-01 length_um 3.25→7）只存在于服务端落库记录  [C7]
历史上下文演练通过：结构漂移与数据变化下，两种保存位置的假成功恢复均按预期复现（C1-C7）
```

两次假成功的机理：

- **C3（浏览器 × 结构漂移）**：草稿只存表单字段。恢复进新编辑页时，隐藏摘要字段由服务端按**当前**目录渲染（`recipe_editor.html:8`），草稿里的旧 token `0:assay` 被回填进新摘要的表单。提交、登记、试算、封存全部 2xx，但 `0:assay` 已从 substrate→assay 变为 cassette→assay，闭包从 5 行塌缩为 1 行。登记校验（`recipe.py:40`）只问"token 存在吗"，不问"它还是原来那条关系吗"。**证据（提交成功、摘要匹配、封存完成）样样齐全，却一样都不支撑"这是操作员原来的判断"。**
- **C6（服务端 × 数据变化）**：会话落库时把"当前源计数"一并缓存。数据变化不改结构，恢复校验（两个捕获 id 存在 + 摘要一致）全部通过，缓存计数被当作当前状态呈现——但摘要从不覆盖数据内容，当前试算计数已经不同。**校验全绿，证据（摘要一致）对它要担保的判断（上下文仍然成立）无效。**

注意 C2/C4：现有 409 防线对**过期标签页原样提交**和**已登记配方**有效，唯独不覆盖**未登记草稿的恢复路径**——假成功发生在防线之外，这正是需要决策记录而不是一句"已有摘要校验"的原因。

## 5. 可保障的重放范围（按保存位置分列）

### 浏览器保存能保障

- 同一浏览器配置文件内，草稿字段逐字重放。
- 不透明引用（捕获 id、配方 name+version）重放为**服务端重新求值**；不可变封存物（行、证据弧、证书、两捕获对比结果）经重取逐字节一致（C7：A×B 对比重放逐字相同）。

### 浏览器保存不保障

- 跨设备、跨配置文件、浏览器数据清理后的任何内容。
- 位置 token 的语义（C1：外键 id 随子句顺序翻转）。
- 草稿所对照的目录视图内容——服务端不保留历史目录，摘要只能回答"变了"，回答不了"当时看到的是什么"。

### 服务端保存能保障

- 草稿/会话与配方版本、捕获在同一状态库事务边界内整体重放；备份/恢复以状态库文件为界一致。
- 漂移检测本身可重放：保留原始摘要 + 语义身份时，恢复时能响亮失败并给出重定位（C5：token 0→1）。

### 服务端保存不保障

- 源库两次读之间的中间态（`PROJECT_SPEC.md:28`：试算只对应本次读快照）。
- 落库派生结论在数据变化后的当前性（C6）。
- 操作员未提交的击键过程（本来就不该进状态库）。

## 6. 会丢的原判断（按保存位置分列）

### 选浏览器会丢

- **外键 token 的语义**："`0:assay` 当时指 substrate→assay"这一判断，token 只存位置（C1/C3 直接实证）。
- 多标签页之间"哪个页面的目录视图更新"——各标签页独立渲染，草稿同步不同步目录视图。
- 被覆盖前的草稿版本与放弃原因（单值覆盖语义）。
- 对比会话的评审上下文（哪对捕获在评审、结论注释）——换机或清数据即丢（C7 中该注释只存在于服务端落库记录）。

### 选服务端会丢

- 未提交的表单编辑内容（操作员改了但没点保存的选择过程）。
- **"该派生结论对应哪一次读快照"**——一旦把试算计数当上下文落库，快照边界丢失（C6 直接实证）。
- 浏览器会话级状态（哪个标签页、光标位置）——本就不应进状态库。

## 7. 可据何种观测改变选型

| 观测 | 阈值/形态 | 触发的调整 |
| --- | --- | --- |
| 源模式漂移率（`schema_digest` 变化次数/月） | 持续 > 1 | 浏览器草稿必须强制语义身份 + 恢复硬校验（向服务端方案靠拢） |
| 恢复/提交路径 409（`browser_schema`、`schema_conflict`）出现率 | 漂移率非 0 而 409 长期为 0 | 说明恢复路径在静默绕过校验（C3 已在生产发生），立即整改恢复路径 |
| 同一配方名的并发草稿数、草稿丢失工单量 | 超团队可容忍阈值 | 草稿服务端化（带版本与合并） |
| 对比会话复访内容 | 要求"当时源状态"的复访占比高 | 会话必须服务端物化并标注读快照边界；纯引用式不够 |
| 状态库体积增长 vs 备份窗口 | 草稿/会话挤占备份保留策略 | 草稿留浏览器，或历史库与状态库分离 |
| 离网/无服务端可达的操作占比 | 高 | 浏览器侧必须保留完整草稿正文与只读封存副本 |

## 8. 备选方案与未采纳原因

- **A. 全部浏览器**：多标签体验最好，但证据性上下文无权威副本，C3 类假成功无解，跨机即丢。不采纳为唯一方案。
- **B. 全部服务端**：恢复校验证据最全，但多标签草稿需建模并发写与未提交状态；且 C6 表明落库派生结论会引入新的假成功；未提交内容仍丢。不采纳为唯一方案。
- **C. 分层放置 + 恢复校验契约（采纳）**：见 §3。位置决定哪类证据天然可得，契约堵住两类假成功。
- **D. 只存引用不存正文**：最省，但草稿正文丢失即工作丢失，多标签场景不可用。不采纳。
